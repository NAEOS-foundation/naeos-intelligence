## 1. Purpose

This document defines the initial API contract for NAEOS Intelligence.

It establishes a consistent interface for:

- Submitting intelligence requests.
- Retrieving request status and results.
- Accessing generated plans and evidence references.
- Managing request cancellation.
- Integrating NAEOS Core, NAEOS CRM, and authorized external clients.

This document defines the conceptual API contract for the MVP. Detailed endpoint schemas and implementation-specific behavior must be validated through the OpenAPI specification.

## 2. API Design Principles

The API MUST follow these principles:

1. **API-first:** Interfaces must be defined before implementation.
2. **Explicit contracts:** Request and response structures must be documented.
3. **Versioned interfaces:** Breaking changes must be introduced through a new API version.
4. **Secure by default:** Every non-public operation requires authentication and authorization.
5. **Least privilege:** Clients may access only resources and operations permitted by their identity and policy.
6. **Asynchronous execution:** Long-running intelligence requests must not require a client to maintain an open connection.
7. **Evidence-oriented results:** Outputs should include references to supporting evidence where applicable.
8. **Policy enforcement:** API access must not bypass the policy enforcement layer.
9. **No implicit execution:** Submitting an intelligence request does not authorize arbitrary execution.
10. **Consistent errors:** API errors must use a stable, machine-readable format.

## 3. API Base Path and Versioning

The initial API version is:

`/v1`

Example base path:

`/api/v1`

The deployment may expose a different external prefix, but the logical API version must remain `/v1`.

### Versioning Rules

- Non-breaking additions may be introduced within the same major API version.
- Breaking changes require a new major version.
- Deprecated endpoints must have a documented migration path.
- Clients must not depend on undocumented response fields.
- API compatibility must be validated through automated contract tests.

## 4. Authentication and Authorization

All intelligence operations must require authentication.

The initial authentication mechanism is an architectural decision to be finalized. Candidate mechanisms include:

- OAuth 2.0 / OpenID Connect.
- Service-to-service authentication.
- Short-lived signed access tokens.

The final implementation must define the supported authentication mechanism and token validation requirements.

### Authorization Requirements

The API must enforce authorization based on:

- Client identity.
- Tenant or organizational scope, if applicable.
- Requested operation.
- Resource ownership.
- Applicable policy.
- Role or permission assignments.

A client must not be able to access another client's intelligence request by guessing its identifier.

### Security Requirements

- Credentials must not be included in request bodies unless explicitly required by a separately approved contract.
- Tokens must not be written to application logs.
- Authorization must be checked on every protected resource operation.
- Missing or invalid authentication must fail closed.
- Unauthorized access must not reveal sensitive resource information.

## 5. Core Resources

The initial API defines the following conceptual resources.

| Resource | Description |
|---|---|
| Intelligence Request | A submitted request for read-only analysis and intelligence processing in the MVP |
| Intelligence Result | The output produced by a completed request |
| Plan | A proposed sequence of steps generated by the intelligence layer |
| Evidence Reference | A reference to source material or observations supporting an output |
| Request Status | The lifecycle state of an intelligence request |

These resources may be represented through dedicated API endpoints or embedded in response objects where appropriate.

## 6. Intelligence Request Lifecycle

The initial request lifecycle is:

`accepted → queued → running → completed`

Additional terminal or exceptional states include:

- `failed`
- `cancelled`
- `requires_approval` (reserved for separately accepted later-phase governed workflows; not an enabled MVP state)

The lifecycle must be implemented consistently across API responses and internal workflow state.

### State Definitions

| State | Meaning |
|---|---|
| `accepted` | The request has passed initial validation and has been accepted |
| `queued` | The request is waiting for processing |
| `running` | The request is currently being processed |
| `completed` | Processing completed successfully |
| `failed` | Processing failed |
| `cancelled` | Processing was cancelled |
| `requires_approval` | Reserved for later-phase workflows; not available in the read-only MVP |

The API must not report a request as `completed` if its required processing has not completed.

A transition to `requires_approval` must not be interpreted as authorization to proceed.

## 7. Endpoint Definitions

### 7.1 Submit an Intelligence Request

**Endpoint**

`POST /v1/intelligence/requests`

**Purpose**

Submit a new intelligence request for processing.

**Request Headers**

- `Authorization`: Required authentication credential.
- `Content-Type`: `application/json`.
- `Idempotency-Key`: Recommended for clients that may retry submissions.

**Request Body**

```json
{
  "purpose": "Analyze repository engineering risks",
  "context_sources": [
    {
      "type": "repository",
      "reference": "naeos"
    }
  ],
  "execution_mode": "analysis_only",
  "desired_outputs": [
    "risk_assessment",
    "recommendations"
  ],
  "metadata": {
    "source_system": "naeos-core"
  }
}
```

**Field Definitions**

| Field | Type | Required | Description |
|---|---|---|---|
| `purpose` | string | Yes | The objective of the intelligence request |
| `context_sources` | array | No | References to authorized information sources |
| `execution_mode` | string | Yes | Requested processing mode |
| `desired_outputs` | array | No | Requested output categories |
| `metadata` | object | No | Non-sensitive client metadata |

Supported MVP execution mode:

- `analysis_only`

`analysis_only` requests analytical processing using authorized read-only retrieval and analysis. It MUST NOT initiate write operations or consequential actions.

The `governed` execution mode is deferred to a separately accepted later phase and MUST NOT be exposed as an enabled MVP mode. Future support will require accepted authorization, approval-state, audit/evidence, and runtime enforcement contracts.

**Successful Response**

HTTP `202 Accepted`

```json
{
  "request_id": "intreq_01HXYZ",
  "status": "accepted",
  "created_at": "2026-11-04T10:00:00Z",
  "status_url": "/v1/intelligence/requests/intreq_01HXYZ"
}
```

The response confirms acceptance of the request, not successful completion.

### 7.2 Retrieve an Intelligence Request

**Endpoint**

`GET /v1/intelligence/requests/{request_id}`

**Purpose**

Retrieve the current status and available information for a submitted request.

**Successful Response**

HTTP `200 OK`

```json
{
  "request_id": "intreq_01HXYZ",
  "status": "completed",
  "purpose": "Analyze repository engineering risks",
  "execution_mode": "analysis_only",
  "created_at": "2026-11-04T10:00:00Z",
  "updated_at": "2026-11-04T10:05:00Z",
  "result": {
    "summary": "Repository analysis completed.",
    "outputs": [
      {
        "type": "risk_assessment",
        "reference": "result_01HXYZ"
      }
    ],
    "evidence": [
      {
        "type": "repository_reference",
        "reference": "evidence_01HXYZ"
      }
    ]
  }
}
```

The `result` field may be absent while processing is incomplete.

The API must return only information that the authenticated client is authorized to access.

### 7.3 Cancel an Intelligence Request

**Endpoint**

`POST /v1/intelligence/requests/{request_id}/cancel`

**Purpose**

Request cancellation of an intelligence request.

Cancellation is a request to stop processing. It is not a guarantee that all underlying operations can be immediately terminated.

**Successful Response**

HTTP `202 Accepted`

```json
{
  "request_id": "intreq_01HXYZ",
  "status": "cancelled",
  "message": "Cancellation request accepted."
}
```

The implementation must define behavior for requests that are already completed or failed. Any later-phase approval workflow is outside the MVP cancellation contract.

Cancellation must not bypass the runtime's safety controls.

### 7.4 Health Check

**Endpoint**

`GET /v1/health`

**Purpose**

Provide a basic service health status.

**Successful Response**

HTTP `200 OK`

```json
{
  "status": "healthy"
}
```

The health endpoint must not expose credentials, internal configuration, sensitive infrastructure details, or user data.

A separate readiness endpoint may be introduced for deployment orchestration.

## 8. Standard Error Contract

API errors must use a consistent machine-readable structure.

The initial format is based on the Problem Details convention.

**Example**

```json
{
  "type": "https://naeos.dev/problems/validation-error",
  "title": "Validation Error",
  "status": 400,
  "code": "INVALID_REQUEST",
  "detail": "The execution_mode field is invalid.",
  "request_id": "intreq_01HXYZ"
}
```

### Error Fields

| Field | Type | Description |
|---|---|---|
| `type` | string | URI identifying the error category |
| `title` | string | Human-readable error title |
| `status` | integer | HTTP status code |
| `code` | string | Stable application-specific error code |
| `detail` | string | Safe description of the error |
| `request_id` | string | Correlation identifier, when available |

### Standard Error Codes

| HTTP Status | Error Code | Meaning |
|---|---|---|
| 400 | `INVALID_REQUEST` | Request validation failed |
| 401 | `UNAUTHENTICATED` | Authentication is missing or invalid |
| 403 | `FORBIDDEN` | The client is not authorized |
| 404 | `RESOURCE_NOT_FOUND` | Resource does not exist or is not accessible |
| 409 | `CONFLICT` | Request conflicts with the current resource state |
| 413 | `PAYLOAD_TOO_LARGE` | Request payload exceeds the allowed limit |
| 422 | `UNPROCESSABLE_REQUEST` | Request is syntactically valid but cannot be processed |
| 429 | `RATE_LIMITED` | Client exceeded the allowed request rate |
| 500 | `INTERNAL_ERROR` | Unexpected internal failure |
| 503 | `SERVICE_UNAVAILABLE` | Service is temporarily unavailable |

Error responses must not expose stack traces, internal secrets, or sensitive implementation details.

## 9. Idempotency

Request submission should support idempotency to reduce duplicate processing during client retries.

When an `Idempotency-Key` is supplied:

- The key must be scoped to the authenticated client.
- Repeated submissions with the same key and equivalent request payload should return the original request reference.
- Reusing the same key with a materially different payload should return a conflict.
- Idempotency retention must be documented by the implementation.

The exact retention period remains an implementation decision.

## 10. Request Validation

The API must validate:

- Required fields.
- Field types.
- Maximum payload size.
- Supported execution modes (MVP: `analysis_only` only).
- Supported output types.
- Context source formats.
- Client authorization for referenced sources.
- Metadata constraints.

Invalid requests must be rejected before intelligence processing begins.

Input validation must not be treated as a replacement for policy enforcement.

## 11. Rate Limiting and Resource Controls

The API must support configurable limits for:

- Requests per client.
- Concurrent intelligence requests.
- Request payload size.
- Processing duration.
- Context source volume.
- Output size.

Rate limiting must be enforced server-side.

When a rate limit is exceeded, the API should return HTTP `429 Too Many Requests`.

Where applicable, the response may include:

- `Retry-After`
- Rate-limit metadata

The initial numeric limits are implementation-specific and must be documented before production deployment.

## 12. Observability and Correlation

Every API request must be associated with a correlation identifier.

The implementation should support:

- Request ID propagation.
- Structured logs.
- Distributed tracing.
- Metrics for request latency and outcomes.
- Correlation between API requests and internal workflow execution.

Correlation identifiers must not contain sensitive user information.

Sensitive request contents must not be logged by default.

## 13. API Security Requirements

The API must comply with the following requirements:

1. All non-public endpoints require authentication.
2. All resource access requires authorization.
3. Input validation must occur before processing.
4. Sensitive data must be protected in transit.
5. Sensitive data must not be exposed through error responses.
6. API operations must not bypass policy enforcement.
7. Any future consequential operation must require appropriate authorization and approval; such operations are not enabled in the read-only MVP.
8. The API must not expose unrestricted execution capabilities.
9. Request and response logging must follow the security requirements document.
10. API behavior must fail closed when authorization or policy evaluation cannot be completed.

## 14. OpenAPI Specification

A machine-readable OpenAPI specification must be maintained alongside this document.

Expected location:

`api/openapi.yaml`

The OpenAPI specification must include:

- API metadata.
- Version information.
- Endpoint definitions.
- Request schemas.
- Response schemas.
- Authentication schemes.
- Error schemas.
- Required and optional fields.
- Examples.
- Validation constraints.

The OpenAPI specification is the implementation-level contract.

This document defines the API design principles and intended behavior. Any material divergence between this document and the OpenAPI specification must be reviewed and resolved.

## 15. Compatibility and Change Management

API changes must be reviewed for:

- Backward compatibility.
- Security impact.
- Client impact.
- Data model impact.
- Operational impact.

Breaking changes must not be introduced silently.

Changes to authorization behavior, request lifecycle, execution modes, or result semantics require explicit review.
